## 1. 結論

**刃先は「屋根の太陽光を降ろす」のまま変えない。骨格を「近接固定費の割り勘エンジン」として見せる。** 太陽光撤去は、足場・車両・処分運搬・班出動という「隣の家までの距離・接道の幅・家の高さで決まる固定費」を束で割る最初の工種にすぎず、同じエンジンに単価表と適格判定を差し替えるだけで、屋根塗装・葺き替え、1980 年代の太陽熱温水器の撤去、災害後の屋根応急修理が同じ画面で動く。

ブラッシュアップの核は 3 つ。

1. **複合束「屋根の上の全部を、一回の足場で」**: パネルを降ろす週は、屋根を塗る・葺き替える週でもある(パネルの下は塗れない)。同じ足場で撤去と塗装を束ねると、撤去単独では出ない安さが出る。これは太陽光という刃先を薄めず、むしろ「いま降ろす理由」を強める。
2. **時間軸の弱点を「先輩」で埋める**: 2013 年設置パネルの撤去本格化は 2030 年代半ば(final/01 §4)。しかし 1980 年前後に大量に載った**太陽熱温水器**は既に寿命を 30 年以上超え、重量物(タンク込み 100〜200 kg 級 [仮定・要確認])が屋根に残っている。同じ「屋根の上の設備を足場と車で降ろす」物理で、需要は**今**ある。築年クラスタ(1975〜1990 年築)で種が見つかる点も同じ。
3. **両面市場の立ち上げを「供給主導の束」で解く**: 事業者が「来週この街区に足場が架かる・トラックが来る」枠を先に出し、既に受注した 1 軒を種に近隣へ招待状を配る。工事看板と近隣挨拶という既存の営業慣行に乗るので、住民側が先に集まるのを待たなくてよい。

**応募戦略**: 一般部門に完成プロダクトとして応募する(本線)。自治体共創部門は、10 月末までに自治体担当者との合意が取れた場合に限り「災害後の応急修理の束発注」を提案として別エントリーする。取れなければ一般部門の資料に「公共適用」を 1 枚入れるにとどめる(§5)。

## 2. 中核の抽象 — 近接固定費の割り勘エンジン

### 2.1 固定費の種類と、それを決める PLATEAU 属性

| 固定費 | それを決める物理 | PLATEAU の属性(実装で使用中=●、加点候補=○) |
|---|---|---|
| 足場の搬入・架払い | 外壁面積、隣棟間隔(連棟移設の可否)、高さ | ● LOD1 外周 × 高さ(`bldg:measuredHeight` / `storeysAboveGround`)、● LOD1 輪郭間の最短距離、○ LOD2 屋根面(屋根側の部分架けの面積、パネル枚数の上限) |
| 車格と台数 | 接道幅員、勾配、積載(枚数・体積・重量) | ● `uro:RoadStructureAttribute/width` → `widthType`(同梱 codelist)→ 家の前の道路面の弦長(tran LOD1)、● dem(勾配で 1 段落とす) |
| 処分運搬のトリップ | 台数、産廃の品目(混載可否) | ● 台数は上と同じ、品目は工種の属性 |
| 班の出動 | 1 日に回れる軒数 | (属性非依存。束の軒数と巡回順で決まる) |
| 束の種(同時期性) | 築年、設備の設置年代 | ● `bldg:yearOfConstruction` の街区クラスタ(道路で区切った区画単位) |
| 優先度 | 放置リスク | ● `uro:BuildingRiverFloodingRiskAttribute`(浸水想定)、○ 通学路(自治体データ) |

### 2.2 工種を足すときに変わるもの・変わらないもの

| 変わらない(エンジン) | 変わる(工種プラグイン) |
|---|---|
| 隣接グラフ、街区クラスタ、車格判定、ビンパッキング、班日、段差の生成、招待状、発注仕様、巡回順、束ストア、事業者ダッシュボード | 単価表(足場が要るか・屋根側だけか、積載の単位、処分の品目、班の 1 軒あたり時間)、適格判定(築年レンジ・階数・浸水など)、同時期性の種(築年か設置年か)、画面の言葉(「降ろす」「塗る」) |

この分離は既に `RateTable` と `PanelInstallation` に半分できている。§8 で `WorkType` として型にする。

### 2.3 一言

> 載せるときは一軒ずつ載せた。降ろすのは、ご近所で。——足場と車は、隣の家までの距離で値段が決まる。PLATEAU はその距離を全国 300 都市で持っている。

審査員向けの補助線: 「太陽光撤去は最初の工種。同じ足場で塗装も葺き替えも降ろせる」。

**採用の帰結**: 一般部門のデモは「太陽光撤去」を本線に、同じ街区で工種を「屋根塗装」に切り替えると段差が出ること、そして「撤去+塗装の複合束」で 1 軒あたりがさらに下がることを 20 秒で見せる。太陽熱温水器は「1985 年ごろの街区」を選ぶと候補が灯る、という形で時間軸の反論に備える。

### 3.1 複合束の物理(概算)

単価モデル(§docs/pricing-model.md)の式で、同じ家の撤去と屋根塗装を同じ足場で行うと、足場の架払い E と搬入 M を 2 工種で 1 回にできる。撤去単独 12 軒 18.4 万 [実装の計算値] に対し、塗装側の足場(単独で 15〜25 万 [公表相場])が丸ごと不要になるため、**塗装を同時に頼む家にとって撤去の実質負担は足場分だけ下がる**。数字は塗装の単価表を入れてから出す(§8 のスプリントで実装)。ここで捏造しない。

## 4. 両面市場の立ち上げ

案の最大の弱点は「片側が集まるまで価値が出ない」(final/01 §4)。答えを「模擬の束を撮影する」から次に差し替える。

| 施策 | 何が変わるか | 11/19 までに入れる最小機能 |
|---|---|---|
| **供給主導の束** | 事業者が「来週 W47、街区 yc-2013-001 に足場が架かる」枠を先に出す。種は既に受注した 1 軒。住民側は「今週ご近所で足場が架かります。同じ週なら 1 軒 ○万円」を見る | 事業者ダッシュボードに「枠を出す」(クラスタ・週・種の建物・事業者名)。束の `origin: 'resident' | 'contractor'` を追加。住民画面のバッジ文言を出し分け |
| **工事看板・近隣挨拶の再設計** | 招待状を事業者名義でも出せる(高齢者が自分で持ちかける心理的障壁を外す)。看板用 A3 も同じデータから印刷 | 招待状の差出人切替(住民/事業者)。A3 テンプレート 1 枚 |
| **分譲地の名簿 = 築年クラスタ** | ハウスメーカーの OB 施主会、分譲地の管理会社、自治会は、同時期分譲の名簿を既に持つ。PLATEAU の築年クラスタはその名簿を「持っていない側」でも再現する装置 | コードは不要。応募資料のチャネル欄に書く |
| **匿名の候補表示** | 「候補あと N 軒(推定・概算)」は登録前の家を断定しない(実装済み) | 現状維持。プライバシーの説明文を招待状に入れる(済) |
| **事業者の課金** | リード手数料 5% [仮定] のほか、「週の枠の予約」(枠を出す事業者が先に払う)を第 2 の収益に | 応募資料のみ。実装しない |

**主張への影響**: 供給主導の束は「事業者が最初のユーザー」に切り替えるので、両面市場の片側問題を「1 社の営業ツール」に還元できる。審査員の「両面市場は片側が集まるまで価値が出ない」に対する答えになる。

## 5. 自治体共創部門

**出す条件**: 10/31 までに自治体担当者(防災・建築指導・環境のいずれか)と「共創」として名前を出す合意。要件がチーム編成である以上、合意なしの応募はできない。

**出すなら何を**: 「災害後の屋根応急修理の束発注」。災害救助法の応急修理制度は自治体が業者を手配する枠組みだが、発災後は業者不足で着工まで数か月待ちが問題になる(2019 年の房総半島台風で顕在化 [公知・要出典])。エンジンをそのまま当てると、被災街区を築年・屋根形状・幅員で束ね、班と高所作業車の巡回計画を自動で出せる。平時は太陽光・塗装の束、発災時は応急修理の束、というデュアルユースが自治体側の導入理由になる。

**相手の探し方**: PLATEAU 整備都市のうち、(1) `cli ingest` で築年充足率が高い、(2) 2012〜2015 年の分譲が多い郊外を持つ、(3) 浸水想定区域と重なる、の 3 条件で候補を絞る。どの都市が築年を持つかは「取り込んで測る」以外に確かめる方法がない(docs/plateau-data.md §4.4)。候補都市の zip を 3 つ取り込むのに 1 日。

**11/19 までの現実**: 合意形成に 2 か月は短い。プレエントリー(11/6 締切)のサポート窓口経由で自治体紹介を求めるのが最短。取れなければ、一般部門の資料の最後に「公共適用: 応急修理・ブロック塀」を 1 枚入れ、自治体共創部門は来年に回す。

| 年 1,000 束(12,000 軒)はどこから来たか | 出所は無い。取り下げる。代わりに積み上げで示す: 1 都市の築年クラスタ数(取り込みで実測)× 1 クラスタあたりの成立率(未知。共同購入型サービスの実績レンジを要ヒアリング)× 1 束の平均軒数。売上は「1 束のリード価値 約 11 万円 [実装の計算値: 12 軒 × 18.4 万 × 5%]」から逆算し、100 束で約 1,100 万円という「規模感」だけを言う |

## 8. 実装への反映

### 8.1 `WorkType`(工種)の抽象 — 型のスケッチ

```ts
/** 工種プラグイン。エンジン本体(隣接・クラスタ・車格・ビンパッキング・段差)は工種に依存しない。 */
export interface WorkType {
  id: 'solar-removal' | 'roof-paint' | 'solar-thermal-removal' | 'roof-emergency-repair';
  label: string;                 // 「屋根の太陽光を降ろす」「屋根を塗る」
  verb: string;                  // 画面の動詞
  /** 足場が要るか、要るなら屋根側の部分架けか全面か。複合束では同じ家の足場を 1 回にする。 */
  scaffold: 'none' | 'roof' | 'full';
  /** 車両積載の単位と 1 軒あたりの量(枚数・m²・kg)。ビンパッキングはこの単位で行う。 */
  cargo: { unit: 'panel' | 'sqm' | 'kg'; perHouse: (b: Building, input: WorkInput) => number; capacity: Record<VehicleClass, number> };
  /** 産廃の品目。同じ品目なら混載可。 */
  disposalItem: string;
  /** 適格判定: 築年レンジ・階数・浸水など。断定せず「候補」として返す。 */
  eligibility: (b: Building) => { candidate: boolean; reason: string };
  /** 同時期性の種: 築年か、設備の設置年か。 */
  cohort: { by: 'yearOfConstruction' | 'installYear'; window: number; defaultRange?: [number, number] };
  /** 工種ごとの単価表(出所ラベル付き)。 */
  rateTable: RateTable;
}
```

`BundleMember` に `works: WorkType['id'][]` を持たせ、`quoteBundle` は同じ家の複数工種で足場の架払いと搬入を 1 回にする(複合束)。`Staircase` と `LeadSpec` の型は変えない。

## 9. 落とした案とその理由

- **ブロック塀撤去(一般部門で)**: 塀の位置・高さ・種類は PLATEAU の建物属性に無く、自治体の通学路点検データが本体になる。「PLATEAU でなくてもできる」に反論できない。自治体共創部門の候補として残す。
- **空き家の一斉解体**: 所有者が不在で「同じ週に同意」が成立しない。束の主体が住民でなく自治体になり、両面市場の片側がそもそも存在しない。
- **給湯器・蓄電池・V2H・EV 充電器**: 固定費(足場・車格)が小さく、束で割れる部分がほぼ無い。段差が出ないものをデモに入れると「なんでも束ねる」に見えて刃先が薄まる。
- **樹木伐採、浄化槽接続、光引込**: 対象物や需要の駆動が PLATEAU の外(樹木属性の欠落、下水道計画、通信事業者)にある。
- **アスベスト**: 規制と専門性が強く、束の価値は工事でなく事前調査にある。刃先が変わる。
- **除雪・雪下ろし、断熱窓、耐震改修**: 物理は合うが、整備範囲・固定費比率・工事の個別性のいずれかで段差価格が成立しにくい。来年以降の候補として保留。
